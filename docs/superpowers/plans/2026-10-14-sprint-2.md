# Sprint 2 Implementation Plan

> **For agentic workers:** Use executing-plans to implement and verify the tasks below. Independent frontend and documentation work may be delegated after the shared HTTP contract is written. The user approved the proposed architecture and web-first scope on 14/10/2026.

**Goal:** Complete the integrated registration → verification → matching → contract → workout → feedback flow with PostgreSQL and reproducible evidence for the nine Sprint 2 deliverables.

**Architecture:** Preserve React/Vite and its visual language. Add a modular Fastify API, SQL migrations and PostgreSQL. Cookie sessions and server-side authorization protect all mutations and private resources; frontend calls relative `/api` endpoints through Vite's proxy.

**Tech Stack:** TypeScript, React, Fastify, pg, Zod, PostgreSQL, Vitest and Playwright.

## 2. Database and API foundation

Files: `server/db/{pool,migrate,seed}.ts`, `server/db/migrations/001_initial.sql`, `server/{app,index}.ts`, `server/shared/{security,errors,validation}.ts`.

- [ ] Create users, profiles, sessions, verification requests/audit, contracts, workouts/exercise blocks, metric catalog and executions, with foreign keys and uniqueness constraints.
- [ ] Each migration runs under a PostgreSQL advisory lock in a transaction and records its version. Seed is explicit and repeatable; credentials come from development environment/configuration.
- [ ] Implement hashed passwords, expiring opaque sessions whose hashes are persisted, cookie flags, mutation origin checks, rate limiting and generic public errors.
- [ ] Implement a transaction helper with one pg client per transaction:

```ts
const client = await pool.connect()
try {
  await client.query('BEGIN')
  const result = await work(client)
  await client.query('COMMIT')
  return result
} catch (error) {
  await client.query('ROLLBACK')
  throw error
} finally {
  client.release()
}
```

- [ ] Verify migrations twice without destructive reset and verify that login failure never returns session or password material.

## 3. Domain and REST routes

Files: `server/modules/{auth,profiles,verification,matching,contracts,workouts}.ts`; shared HTTP contract.

- [ ] Auth endpoints create athlete/coach only, load session and invalidate on logout. Normalize email and reject duplicates.
- [ ] Profiles persist matching preferences. Verification submission moves trainer to pending; administrator decision writes audit and status atomically.
- [ ] Calculate match only for approved, compatible trainers: goal 30, level 20, budget 25, availability 25; stable tie-breaking by name/id.
- [ ] Contracts are pending/active/rejected. Conditional updates and a unique athlete/coach pair prevent duplicate acceptance. A rejected pair can be requested again without bypassing approval.
- [ ] Workouts belong to active contracts. Drafts are private to the coach, publication requires valid exercises; executions accept only the owning athlete and supported metrics with valid limits.
- [ ] Add authenticated dashboard data and metrics catalog; expose route schemas as OpenAPI.
- [ ] API checks must include `expect(response.statusCode).toBe(403)` for cross-role operations and 404 for another user's private workout; persistence must survive constructing a new app instance.
